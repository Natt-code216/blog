# 为什么需要前端架构

在讨论"怎样做架构"之前，我们先用一整章回答更朴素的问题：项目变大之后，到底卡在哪里？

如果回答得很模糊——"代码很乱"、"耦合太多"、"新人上手慢"——这些描述往往是症状的果，不是因。架构想解决的，是那些"看每一处单独都合理、合在一起却出问题"的结构性问题。

## 一个真实的症状清单

我把过去几个团队里反复出现的"项目变难改"的征兆列在下面。它们不是 bug，是结构上的征兆，越早识别越好处理。

**1. 新功能落地时间不再正比于功能复杂度**
两周前那个"加一个筛选项"的需求做了 3 天。这周一个看起来更简单的"加一个空状态"也做了 3 天。看起来每个需求成本差不多，但只要把它放在功能复杂度坐标上画一下，你会发现成本曲线已经从近似线性变成了平台——简单需求和复杂需求的成本逐渐趋同，因为大部分成本花在"在这个项目里把改动放对地方"。

**2. 改一处需要改三处**
组件不再独立。改一个按钮样式要顺带改三个调用方；改一个数据字段名要在五个组件里同步改；改一个分页参数要去翻两个 hook、一个 reducer、一个 transformer。这种"修改放大"是耦合的最直观指标。

**3. 新人提的第一个 PR 一定走错路径**
不是新人能力问题，是"这个项目希望你把代码放在哪里"这件事，已经无法通过结构本身被传达。新人凭直觉建立的文件结构，永远和老人维护的那一套不一样，于是每个 PR 都要 review 时大幅返工。

**4. 全局 grep 才能找到入口**
想看一个功能的实现，你的第一反应不是按目录结构往下走，而是 grep。这意味着目录已经不传达任何意图。结构在文件名里、在 import 路径里，但不在目录树里。

**5. 测试覆盖率掉得比写代码快**
不是没人写测试，是写不动了。每写一个新功能就要 mock 七八个上下文，而这些上下文之间还有隐含的顺序。测试的成本超过了功能本身的成本。

**6. 任何"小重构"都会拖出 50+ 文件变更**
重命名一个组件，依赖关系拖一长串。删一个"看上去没人用"的 prop，运行时报错告诉你其实有三个地方在用。"安全重构"已经成了奢侈品。

如果你已经在某个项目里看到上面 6 项中的至少 3 项，恭喜——你已经站在了"需要架构"的门槛上。

## 这些症状的共同根源

把这些症状摆在一起，会发现共同的根源不是"代码质量差"，而是**没有让人能用结构本身来推理代码的边界**。

具体来说，一份能被新人快速读懂的代码库，应该满足三个条件：

- **可定位**：给一个功能名，能在 10 秒内找到它的入口；
- **可隔离**：改一个功能时，能在 30 秒内列出"可能受影响的范围"；
- **可移除**：当某个功能不再需要时，能用半小时把它整段删掉，不留遗骸。

大多数"很难改"的项目，是这三件事都做不到。功能散在多个文件里，没有清晰的入口；改动的影响范围只能凭记忆估算；删除一个功能要在四十处把它的痕迹一个一个剔掉。

架构的工作，本质上就是让这三件事**通过结构本身**就能做到。

## 架构不是"框架"

很多团队把"架构问题"误以为"框架问题"。问题不是 React 太轻，问题不是 Redux 过时，问题不是该不该换 TanStack Query。这些都是工具维度的讨论，不解决结构问题。

我见过一个团队，把项目从 Vue 2 重写为 Vue 3，期待这次"现代化"能让代码重新可维护。半年之后，新项目里出现了几乎相同的症状——因为他们带过去的是同样的目录组织、同样的状态散落方式、同样的组件耦合习惯。

工具升级带来的只有"今天写起来更顺手一点"。结构问题不会因为工具升级而消失。

## 架构是"边界"

如果一定要给"前端架构"下一个最朴素的定义，我倾向于这个：**架构是关于边界的决定**。

具体来说：
- 哪些状态属于全局，哪些属于本地？
- 哪些组件可以跨业务复用，哪些只能在某个业务里被引用？
- 哪些代码可以被多个路由共享，哪些必须随路由按需加载？
- 哪些类型在边界内部用，哪些必须被定义为对外契约？

这每一条都是一个边界。架构做得好的项目，这些边界在代码里**可见**——通过目录结构、通过命名空间、通过显式的 import 限制规则。架构做得不好的项目，这些边界**隐式**——靠记忆、靠口头约定、靠每次 review 提醒。

隐式的东西，迟早会被打破。

## 本章小结：一段伪代码

```ts
// 一个"需要架构"的项目，往往长这样：
features.forEach(feature => {
  feature.codeIsScatteredAcross([
    '/components',
    '/hooks',
    '/utils',
    '/store',
    '/api',
  ]);
  feature.boundariesEnforcedBy('memory + tribal knowledge');
});

// 一个"架构良好"的项目，往往长这样：
features.forEach(feature => {
  feature.codeIsContainedIn(`/features/${feature.name}`);
  feature.boundariesEnforcedBy('directory structure + lint rules');
});
```

注意，这两段伪代码描述的不是工具差别，是**结构哲学**的差别。下一章我们会具体讨论第二种结构在目录层面长什么样、为什么这样组织、以及在过渡阶段如何与第一种共存。

在进入工具细节之前，请先记住本章的一句话：架构是关于边界的决定，工具只是边界的表达方式。换工具不会让边界自动出现，画好边界之后任何工具都能用。
