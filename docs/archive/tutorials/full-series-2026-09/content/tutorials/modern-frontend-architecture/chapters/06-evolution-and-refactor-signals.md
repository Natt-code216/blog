# 架构演进与重构信号

前五章给出了一组架构原则——按业务切片、状态分层、Server State 专用、代码分割、bundle 预算。但任何"原则"放到真实项目里，都会面对一个尴尬的现实：**你接手的项目，从来不是从零开始的**。

它有十万行历史代码、五十个还没机会重写的旧模块、三个早就该删但谁也不敢动的 hack。任何架构演进都不是"切到新方案"，而是"和旧方案长期共存"。

这一章我们讨论两件事：

1. 怎么识别"该重构"的信号；
2. 怎么识别"该忍"的信号。

## 该重构的信号

不是所有"有点丑"的代码都值得重构。值得花精力的，是那些**变更成本不正比于变更内容**的地方。下面是几个高度可靠的信号。

### 信号一：同一个 bug 反复出现在不同 PR 里

如果三个月里有四个不同的 PR 都修了"列表筛选丢失"的问题，那就不是 bug 修不好的问题，是**结构里有一个被反复绕过的洞**。

这种信号最值得重构。原因是：每次修都贵，修了还会回来。一次性把洞补好，长期收益巨大。

具体做法：
- 找到这个 bug 的所有历史 PR，列出共同点；
- 一定有一个被反复绕过的"应该集中、却散落了"的状态或逻辑；
- 把它收敛成一个组件 / 一个 hook / 一段服务层代码。

### 信号二：新人入职第二个月还在问"X 在哪里"

这是结构传达失败的最直接信号。新人第一周问问题是正常的；第二个月还在问"用户认证逻辑在哪里"、"全局错误处理在哪里"，意味着**这些东西不在该在的地方**。

值得做的事：
- 把这些"经常被问"的位置在 onboarding 文档里记一份；
- 但更关键的：把它们重新组织到一个目录树能"猜到"的位置。

### 信号三：测试覆盖率下降但代码量上升

代码越写越多，测试越写越少——这不是程序员变懒，是**测试成本超过了功能成本**。

原因往往是：测试一个新功能需要 mock 越来越多的上下文（context、store、provider、API）。一旦 mock 数量超过功能本身的代码量，写测试就变成一种心理负担。

值得做的事：
- 引入更轻量的测试基建（如 React Testing Library + MSW 模拟 API）；
- 把"上下文依赖"用 wrapper 函数收敛，让测试 setup 缩到几行；
- 鼓励测试单元级别的逻辑，而不是端到端的组件。

### 信号四：一周内有三次"为什么这里要这么写"的疑问

这是"知识无法被代码传达"的信号。如果连写过它的人都需要在 PR 评论里解释三次，那这段代码的设计本身就有问题——不是命名差，是抽象错了。

值得做的事：
- 暂停讨论"该怎么写"，先讨论"为什么这里需要这么写"；
- 90% 的情况下，会发现原本的需求其实可以用更朴素的方式实现；
- 剩下 10% 是真正棘手的边界，需要写文档说清楚。

## 该忍的信号

不是所有"看起来该重构"的代码都值得动。下面是几个**该忍**的典型场景。

### 该忍一：六个月内没人改过的模块

如果一个模块六个月内零改动、零 bug、零客诉，它的"丑陋"对系统没有任何外部成本。它只是看起来不顺眼。

重构这种模块的回报极低。它没有给你带来痛苦，重构它只是满足你的洁癖。同时引入的回归风险却是真实的——它在生产环境跑了半年没炸，重写之后可能炸。

**经验法则**：如果不是为了支持一个明确的新需求，不要重构稳定的旧模块。

### 该忍二：即将被业务砍掉的功能

有时候团队会出现一种集体冲动——"这个功能太丑了，重写一下"。但一问产品，发现这个功能下季度就要下线。

重写一个即将下线的功能，是把工程时间扔进黑洞。这种重写带来的所有收益都会随功能下线一起消失。

**经验法则**：动重构之前，先和产品确认这个功能至少还会活 12 个月。

### 该忍三：架构师本人没法持续投入的重构

一次重大架构迁移，需要至少有一个人持续投入 1–3 个月、专门盯整个迁移的进展、识别风险、和团队成员一对一解答疑问。

如果没有这个人，或者这个人随时可能被抽走，重构最终大概率烂尾——一半模块在新结构里、一半还在旧结构里，比统一在旧结构里更难维护。

**经验法则**：没有"重构负责人"的重构，比不重构更糟。

### 该忍四：业务高速增长期

业务每周都在变需求、每月都在调战略，这种时候做架构迁移，是把脚下的地板换成沙——你今天迁好的部分，下周可能又要因为新需求推翻。

更明智的做法是先抗过这一波，等业务节奏稳定后再做迁移。

**经验法则**：业务节奏剧烈时不动架构，让架构等业务。

## 演进路线的几种健康形态

如果上面的"该重构信号"已经够清晰、"该忍信号"也已经排除，剩下的问题是：怎么演进？

我见过的健康演进路径，基本都是下面这种渐进式：

1. **建一个新结构，先空着**——例如 `features/` 目录，先不放任何东西。
2. **新代码进新结构**——任何新功能、任何新模块，强制走新结构。
3. **借势迁移旧模块**——每次旧模块有大改动，借此机会迁移到新结构。
4. **半年一次集中清理**——把那些"长期不动但又必须保留"的旧代码集中迁移一次。
5. **lint 规则逐步收紧**——一开始只对新结构内部生效，半年后开始限制旧结构对新结构的引用方向。

这种"借势迁移 + 渐进收紧"的方式，比集中式重写便宜一个数量级，也不会引入大爆炸式回归。

## 架构师最重要的能力：克制

写到这一章的最后，我想说一句和前面所有章看似矛盾的话：**架构师最重要的能力，是克制**。

不是"知道更多模式"，不是"画更漂亮的图"，不是"读过更多论文"。是面对一个看起来很丑、很想动手的代码块，能够诚实地问自己——这件事是真的值得改，还是只是我个人想要改？这件事改了之后给团队带来的总体收益（少了多少 bug、节省多少开发时间），是否真的超过了它的迁移成本？

很多优秀的工程师卡在这一步——他们看到太多"可以更好的地方"，但低估了"改它需要付出多少"。结果就是大量启动了一半的重构、半新半旧的目录结构、永远在迁移路上的项目。

好的架构师，在大多数时候是不出手的。出手时，是因为他确认这次改动会给团队带来三年以上的复利。

这就是本系列的最后一句话：架构不是"对正确模式的追求"，而是"对长期成本的诚实"。
