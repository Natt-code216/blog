我做工程师的第三年，遇到过一位同事让我至今难忘。

他比我大十几岁，从某家很老的银行系统转过来。代码写得很慢，每个 PR 都不大，三五个文件，几十行改动。但他的代码进了 review 之后，几乎从来不需要返工——不是因为评审员宽容，而是没有什么可以挑的。每一个变量名都恰到好处，每一段函数的边界都干净利落，连注释都简洁得像电报。

有一次我问他："你怎么能写得这么慢，又这么准？"他放下咖啡，笑了一下，说："我每次合并 PR 之前，会把自己写的每一行从头读一遍。不是为了找 bug——bug 我让 CI 找——是为了确认我愿意为这段文字署名。"

那一刻我突然理解了一件事。写代码不是工程，是手艺。

木匠会在做完一张椅子后，用手摸过每一处接缝。不是为了检查松紧，松紧木匠早就知道。他摸的是"这是不是我满意的状态"。是问自己：明天有人会坐在这上面，三年后这把椅子可能在某个不认识的人家里，那时候我希望它被怎么记得？

写代码的人也是。好的工程师在合并 PR 之前，把每一行从头读一遍——不是为了找 bug，而是确认自己愿意为这段文字署名。

代码是一种留痕。它会被后来者看见。它会在凌晨三点被某个排查事故的人追溯。它会在两年后的某次重构里被翻出来，决定要不要保留。一段代码留下来的不只是逻辑，还有当年那个写它的人的状态——是匆忙还是从容、是清楚还是糊涂、是把后来人当朋友还是当敌人。

举一个真实的小例子。我有一次重构一个支付状态机，把它从 if-else 的嵌套结构改成显式的状态转移表。改之前大概是这样：

```ts
function transition(order: Order, event: Event) {
  if (order.status === 'pending') {
    if (event.type === 'pay') {
      if (event.amount === order.total) {
        order.status = 'paid';
      } else if (event.amount < order.total) {
        order.status = 'partial';
      } else {
        throw new Error('overpay');
      }
    } else if (event.type === 'cancel') {
      order.status = 'cancelled';
    }
  } else if (order.status === 'paid') {
    // ...
  }
}
```

改之后是这样：

```ts
type State = 'pending' | 'paid' | 'partial' | 'cancelled' | 'refunded';
type Action = (order: Order, event: Event) => State;

const transitions: Record<State, Partial<Record<Event['type'], Action>>> = {
  pending: {
    pay: (o, e) =>
      e.amount === o.total ? 'paid' :
      e.amount  <  o.total ? 'partial' :
      (() => { throw new Error('overpay'); })(),
    cancel: () => 'cancelled',
  },
  paid:      { refund: () => 'refunded' },
  partial:   { pay:    completePartial, cancel: () => 'cancelled' },
  cancelled: {},
  refunded:  {},
};
```

行数差不多，但读起来完全不是同一类东西。第一版是"我当时正在解决一个问题"；第二版是"这个领域的规则就是这样的"。前者描述了实现过程，后者描述了不变量。一个新来的同事打开第二版的代码，不需要在头脑里执行 if-else，他可以直接读这张表：哪些状态可以接收哪些事件，转去哪个新状态。这就是"克制"的力量。

代码的优雅，是对未来读者的体贴。它不是写得短，也不是用最巧的语法。它是降低别人的认知成本——让那个凌晨三点排错的人，能少摸黑十分钟；让那个两年后接手的同事，能少猜一次原意；让那个第一次读这段代码的实习生，能感受到"这件事可以做得很清晰"。

我现在写代码，已经不太追求"聪明"。聪明的代码会写起来很爽，但读起来很累——它把作者的兴奋留给了自己，把困惑留给了所有后来者。这种交易在短期里看起来赚了，长期看是亏的。因为代码 80% 的生命周期不是被写的时候，而是被读的时候。

柳宗悦写工艺之道，反复强调"为他人使用"。他说：真正美的器物是匿名的，是日常的，是经得起反复触摸的。好的代码也是这样。它不是炫技，不是签名档，不是某个工程师标榜自己存在感的痕迹。它是干净的、可以被理解的、值得被继承的东西。我希望我留下的就是这样的代码。

那位前辈现在已经退休了。他写过的系统还有几个在跑，听说去年某次大促，他十年前写的那段对账逻辑被一个新人翻出来，没改一行，跑了一夜。新人后来在内部论坛发了一句话："这段代码像被人爱过。"

那一刻我突然觉得，这才是手艺人能听到的、最高的赞美。

我后来翻出当年那位前辈的几个 PR 重新读了一遍。其实并没有什么高超的语法或惊艳的设计。它们只是稳稳的、克制的、像一段段诚实的句子——不耍花招、不堆术语、不替自己邀功。读起来就像他本人那样：慢、准、安静。这种代码不会出现在任何技术大会的分享里，因为它没有什么"亮点"。但它们就是那种你愿意把整个系统的关键路径交给它的代码。这是手艺最朴素的样子，也是我希望自己写代码十年、二十年之后能慢慢靠近的状态。
